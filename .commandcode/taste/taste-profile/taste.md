# Taste Profile
- **Social-feed content model**: Prefers Instagram/Twitter/Reddit-style vertical scroll where each content piece is a visually significant card that "breathes" — not cramped grids or conventional list layouts. Confidence: 0.95
- **Source as author**: Wants content sources to feel like social media authors — logo/avatar at top, name, time, domain — making provenance immediately obvious. Confidence: 0.9
- **AI transparency**: AI-generated content should be clearly labeled (e.g., "✦ AI SUMMARY") and visually distinct from original source material. Confidence: 0.95
- **Signature interactions**: Values a recognizable "Explain this" button as a recurring product differentiator across all content cards. Confidence: 0.85
- **End-of-feed ritual**: When content ends, prefers a beautiful completion experience (stats, breathing room, gentle transitions) over a bare "no more items" message. Confidence: 0.9
- **Boomerang/loop transitions**: Likes smooth animated transitions between content states (e.g., end of today → yesterday) rather than hard page changes. Confidence: 0.8
- **Discussion as Reddit-style**: Comment threads should feel like Reddit (sorted, threaded, with likes/replies) rather than generic comment boxes. Confidence: 0.85
- **Multi-source aggregation**: Values showing when multiple sources cover the same story, with agreement/disagreement analysis. Confidence: 0.8
- **Warm caramel/coffee palette**: Prefers warm brown/cream/caramel accent colors over cool or neon palettes. Confidence: 0.9
- **Editorial typography**: Uses serif fonts (Newsreader) for headlines and sans-serif (Inter) for UI — creates a magazine-meets-tech feel. Confidence: 0.85
- **Soft, rounded UI**: Rounded cards (20px+ radius), subtle borders, soft shadows, smooth scrolling, sticky headers, blurred navigation. Confidence: 0.9
- **Image-first content**: Every card should feature a prominent image (16:9 article thumbnails, hero images, source branding). Confidence: 0.9
- **Light + dark themes**: Expects both with smooth transitions and theme-appropriate color adjustments. Confidence: 0.85
- **SaaS/consumer startup feel**: Products should feel like polished consumer startups, not dashboards, admin panels, or static readers. Confidence: 0.9
- **Frontend-first demos**: Prefers fully functional frontend-only implementations deployable to GitHub Pages before adding backend. Confidence: 0.9
- **localStorage persistence**: Uses localStorage for demo-mode state (likes, saves, theme) when no backend exists. Confidence: 0.85
- **React + Vite stack**: Default tooling for new projects. Confidence: 0.8
- **Sample data enrichment**: Extends base data with demo-only fields (images, social counts, discussions) rather than leaving empty demonstrations. Confidence: 0.85
- **Demo mode transparency**: Clearly labels demo/sample data with badges and messaging about free infrastructure limitations. Confidence: 0.8
- **Detailed structured specs**: Provides comprehensive product specifications with ASCII art mockups, data models, and phased implementation plans. Confidence: 0.95
- **Product references**: Frequently references existing products (Instagram, Twitter, Reddit, Apple News, ChatGPT, Perplexity) to communicate desired feel. Confidence: 0.9
- **User-flow thinking**: Describes features as user journeys (open app → scroll → interact → reach end) rather than feature lists. Confidence: 0.85
- **Visual hierarchy emphasis**: Explicitly states what should be visually dominant vs. subtle, and what to avoid (no dashboards, no neon, no cramped cards). Confidence: 0.9
- **Full UI responsiveness (practical, self-adjusting)**: Expects the entire UI to be responsive across screen sizes, and wants it to feel practical — self-adjusting layouts with mobile-friendly navigation (hamburger/drawer, accessible menus), no dead space from `display:none` columns eating viewport, no overflowing text/buttons. Not satisfied with technically-present media queries that leave the mobile experience broken. Confidence: 0.95
- **Honest status indicators**: Service/status indicators must reflect real verification (actual health checks / live probes), not assumed "live" state — shows strong dislike for fake or hardcoded "online" statuses. User explicitly insists on verifying first before reporting status. Confidence: 0.97
- **Professional polish**: Wants the UI to feel professional and production-quality, not demo-grade or sloppy. Confidence: 0.85
- **Graceful API fallback**: When backend is offline, slow, returns 5xx, times out, or returns malformed data, app must gracefully fall back to sample/demo data with a subtle user-facing message ("Live research is temporarily unavailable") rather than crashing or showing raw errors. Confidence: 0.95
- **No secrets in frontend code**: Strong security stance — never put API keys, tokens, or provider credentials in `.env`, `VITE_*` vars, or frontend code; anything bundled into the frontend (including Vite env vars) is public after build. Only public service URLs belong there. Confidence: 0.95
- **Backend orchestration boundary**: Frontend should not duplicate backend orchestration logic — do not call downstream services (LLM, search, crawlers) directly from the browser when an orchestrator already fronts them. Always go through the documented orchestrator API. Confidence: 0.9
- **Centralized API layer**: Prefers a single config file for service URLs plus a dedicated `services/` or `api/` directory; raw `fetch()` calls scattered through UI components are an anti-pattern. Confidence: 0.9
- **Health-check polling etiquette**: Periodic health checks should be polite (30–60s intervals), pause when the browser tab is hidden via `document.visibilityState`, and allow a manual refresh — don't hammer endpoints just because the URL exists. Confidence: 0.85
- **Cold-start patience UX**: For free-tier / sleep-prone hosting, show progressive "waking up..." messaging after a few seconds before declaring an error, recognizing that initial requests legitimately take longer. Confidence: 0.85
- **Request cancellation hygiene**: Use `AbortController` to cancel in-flight requests when a new one starts; debounce/disable submit buttons to prevent duplicate submissions. Confidence: 0.85
- **Defensive API response handling**: Don't assume API responses are well-formed — validate expected fields, provide safe defaults (empty arrays/objects), and render unknown asset/content types via generic fallbacks rather than crashing. Confidence: 0.9
- **Mode indicator visibility**: When an app has multiple data modes (Demo vs Live), surface a subtle badge/label so users know what they're seeing, with clear messaging on mode switches and on fallback from Live → Demo. Confidence: 0.85
- **Technical status stays secondary**: Even when adding real backend integration, service status, API health, and infrastructure indicators must not dominate the consumer experience — news/content remains primary, infrastructure is discoverable but unobtrusive. Confidence: 0.9
- **CORS-aware frontend UX**: When a deployed API may not allow the frontend origin (e.g., GitHub Pages), surface a clear "the service needs to allow this origin" message rather than mislabeling it as an LLM/API failure or attempting unsafe workarounds. Confidence: 0.8
- **Visual symptom bug reports**: Reports UI bugs by describing what he sees rather than the technical cause — pastes the rendered text/content of a broken component and adds the symptom ("on pc its hiding behind the cards"). Expects the assistant to translate the visual symptom into the underlying CSS/layout root cause (stacking context, containing block, z-index, clipping) and fix it. Confidence: 0.85
- **Fix every breakpoint in one pass**: When reporting a defect, expects it addressed across all screen sizes at once ("show it on smartphone too and on pc ... fix that") — a fix that only works on one breakpoint is incomplete. Confidence: 0.9
- **Overlays must float above everything**: Popovers, status panels, and drawers should escape their parent's clipping/scroll container (`position: fixed`, high z-index) and sit above cards and bottom nav — never trapped inside a sticky/overflow ancestor. Confidence: 0.85

- **Auto-push follow-up fixes**: After an initial explicit "publish it to github", expects subsequent related fixes to be committed and pushed automatically without asking again. Confidence: 0.8
- **Terse, directive communication style**: Writes short, imperative commands with frequent typos and missing spaces ("publosh it to github", "the uiis not mobile or screen freindly make itpracrical so that it adjust itlsetf fix that"). Prefers the assistant to interpret intent without asking clarifying questions, infer the obvious fix, and execute end-to-end rather than discuss options. Confidence: 0.85
